# 处理阶段使用显式状态机

资料有六个处理阶段。即使规模很小，也使用 `github.com/looplab/fsm v1.0.4`（Apache-2.0）集中声明跳转表，让成功、失败与恢复路径使用同一份合法性校验，避免处理器的分支自行推断阶段。

| 事件 | 原阶段 | 新阶段 |
| --- | --- | --- |
| `pass` | `new` | `prefiltered` |
| `block` | `new` | `blocked` |
| `analyze` | `prefiltered` | `analyzed` |
| `publish` | `analyzed` | `done` |
| `fail` | `new`、`prefiltered`、`analyzed` | `failed` |

`blocked`、`done`、`failed` 是终点。重试不是事件，只记录次数、下次时间和错误，保留原阶段。两次评分和写作中的最后一项成功保存时，在同一条数据库更新中保存 `analyzed`。领取到三项已保存但仍为 `prefiltered` 的资料时，先补 `analyze`，不重复请求模型。

## 职责边界

- biz 的处理阶段模块只按当前阶段创建状态机、触发事件并返回新阶段；库的任何错误统一视为非法跳转，不注册回调。
- biz 的 Processor 负责模型请求、两次评分与写作的并行、保存顺序、重试退避及事件选择。模型请求仍并行，保存和已完成进度的更新串行，避免两个步骤同时认为自己是最后一项。
- data 负责领取、advisory 锁、比较并替换与落库。每一步保存、归组事务内的发布、每轮结束的记账，都以原阶段为更新条件。更新 0 行时返回冲突并记录错误日志，不覆盖当前资料。归组仍在事务外请求模型，在事务锁内重验候选并原子提交事件、代表资料、公开阶段与处理时间。

每轮成功时只记账，公开结果由归组事务保存；记账失败不撤销已发布资料。取消不增加尝试次数，并释放资料锁。无法解码的已存事实按永久失败处理，不阻塞后续资料。

## 代价与并发约束

代价是多一个依赖；手写这张表只需十几行，也能够实现当前需求。选库是为了把跳转及其合法性显式集中，而不是为了引入回调框架或额外流程。

状态机实例只用于一次纯阶段计算。库本身不提供数据库并发一致性；并发安全仍依靠 PostgreSQL 的比较并替换、队列行锁、资料 session advisory lock 与归组事务 advisory lock，继续遵守 [ADR-0002](0002-gorm-model-migrations.md)。不会把模型请求或数据库写入放进状态机回调。
