# 用 GORM 模型维护表结构

Vane 已选择 GORM 作为数据访问层，表结构也由 `internal/data/models.go` 和 `AutoMigrate` 维护，避免同时维护模型与手写建表 SQL。开发阶段模型的约束或取值变化时，直接重置开发库，不写迁移。项目仍在开发阶段，不保留旧 SQL、迁移账本和历史数据回填，也不提供旧版本数据兼容流程；删除这些代码不会主动删除运行库的数据或表。

业务表的结构迁移与外键补齐在同一个 PostgreSQL advisory 事务锁内执行。资料与事件存在双向外键，因此先建立全部表，再按模型关系创建外键；模型明确声明 `GENERATED ALWAYS AS IDENTITY`、`TEXT[]`、`JSONB`、无穷时间默认值、CHECK 和部分索引。重复迁移只维护结构，不改写资料的处理状态或信源调度时间。GORM 的自动迁移行为见[官方说明](https://gorm.io/docs/migration.html)，模型修改仍需结构、约束和幂等测试验证。

普通查询使用模型、类型化投影和子查询，公开列表不读取正文，也不逐条补查信源或事件。队列领取使用 GORM 的 `FOR UPDATE OF i SKIP LOCKED` 子句；处理期间的 session advisory lock 仍绑定专用连接，事务提交后继续持有，取消时释放，释放失败则丢弃连接。数据库特有的锁表达式保留 SQL，不模拟为进程内锁。

归组模型判断在事务外完成；提交时在全局事务 advisory lock 内重新召回候选，比较候选 ID、内容、相似度和顺序。候选变化时退出事务并有界重判，避免同时看到空候选的任务重复新建同一事件，同时不让慢模型请求占用事务和全局锁。代表资料与公开状态仍在同一事务提交。

信源模型独立保存 `retry_not_before`，把服务器要求的最早重试时间与普通采集周期区分开。改变采集周期时重新计算调度，但不能越过该时间；改变 FeedURL 时清空旧地址的缓存和调度状态，历史资料保留。新增字段继续由 AutoMigrate 维护。
